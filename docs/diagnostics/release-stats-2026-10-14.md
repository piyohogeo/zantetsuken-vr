## 9. 8章までを受けた判断（2026-10-14、TL）

- **時間の軽さは、この段階でいったん受け入れる。** サンプラを含むサービスの更新が平均約0.013 msなら、これを削る最適化は優先しない。この値は計時した区間の経過時間で、Renderスレッド・GPUを含む総費用ではない。
- **ON／OFFの比較は参考の扱い。** 起動の時間帯が離れたことと、PCの使用の影響がある。追加のON／OFFの測定はしない。統計OFFの回の315.6 msのフレームは原因不明として残し、統計の採否を止める理由にしない。
- **Playerでの確保は、測り方が成立してから確かめる。** 要るもの：対象のIL2CPP Playerで確保を検出できる手段、既知の確保を正しく検出する対照、サービス自身の確保とゲーム全体の確保の区別。成立すれば、静止中と切断・構造変更中を同じ短い実行にまとめる。成立しなければ「Playerで未確認」と明記し、0とは主張しない。
- **配布。** PCVRの限定の検証版は可。一般の配布とQuestの完了の判断は別である。一般の配布の前に要るもの：送信先・保持期間・配布用の認証と受信側の制限の確定。試験用のトークンの整理と、配布物への混入の防止。実際に配布する構成での、同意・撤回・終了時の送信の確認。QuestでのQuestの確認。
- **製品に検証用の観測が入らないこと。** 製品Releaseのコンパイル検査が、コンパイルした各アセンブリに検証用の型の名前が無いことを確かめる（Windows 64ビットとAndroid、各11アセンブリ）。記号付きのコンパイルでは、同じ検査が型を見つける。

## 10. Playerでの確保の確認（9章の判断を受けて）

**方法。** エンジンの確保の記録 `GC.Alloc`（Unityの試験の枠組みが確保の検出に使うものと同じ）を、メインスレッドに絞り、サービスの `Update` の前後だけ有効にして、その区間の中の確保の回数を読む。区間とスレッドで、サービス自身の確保をゲーム全体の確保から分ける。この記録はDevelopmentのPlayerにだけあり、Releaseには無いので、検証専用の構成をDevelopmentでビルドした。

**対照。** 同じPlayerの中で、同じ記録で、何もしない区間・1個の確保・3個の確保を測る。0・1・3と読めなければ「Playerで未確認」とする約束で行った。Editorでは、区間を続けて開閉したときに0・1・3・0・1と読め、区間の外の確保がどの区間にも入らないことを試験で確かめてある。

**実行。** Link、`play`（WalkCity）、統計ON、プレイの開始から5秒後に開く60秒の窓。人が斬り続けた1回。例外0、送信なし。

| | 値 |
|---|---|
| 記録の有効 | 有効（Development、IL2CPP） |
| 対照（起動時1回、窓の中21回） | 22回すべて 0・1・3 |
| 窓のフレーム数（統計が数えたフレーム数） | 5,400（5,400） |
| 構造が変わったフレームでのサービスの更新 | 168回、確保0回 |
| それ以外のフレームでのサービスの更新 | 5,232回、確保0回 |
| 窓の中で受理された切断 | 77 |
| ゲーム全体の1フレームの確保（エンジンのカウンタ、前フレームの値） | 最小1,108バイト、平均約170 KB、最大約2.6 MB |

**分かったこと。** IL2CPPのPlayerでこの記録は確保を数える。その記録で、サービスの更新は5,400フレームのあいだ一度も確保していない。構造が変わったフレームでも同じである。同じ窓で、ゲーム全体は全フレームで確保している。

**限界。** DevelopmentのPlayerでの結果である。Releaseでも同じ場所で確保が起きるというのはC#についての前提で、測ったものではない。回数であってバイト数ではない。対象は1分間の `play` で、シーンの切替、XRの状態の変化、最初の呼出し、設計上確保する出来事（フォーカス喪失・終了時の送信のJSON、Worldが新しいときの探索）は含まない。このビルドで出たサービスの更新の時間（平均11.0 µs）はDevelopmentの値で、Releaseの費用ではない。

## 11. Quest 3S での確認（Development、2026-10-14）

街歩き1シーンのAPK（設定で `play`）を、送信設定なしで実機に入れて確認した。Vulkan、フレーム合成あり（45 Hz）。

- **同意ダイアログ。** 初回の起動で表示された。出た直後に頭の前へ置き直され、4.6秒で「Agree」が選ばれた。メニューの「Send play statistics」の項目も見えた（TL）。
- **フォーカス喪失。** システムメニューを開くと `OnApplicationFocus(false)` が来て、記録が出た。Questでは終了時の記録が無いので、これが記録と送信の契機である。Quest 3Sには装着センサが無いので、ヘッドセットを外してもアプリには何も通知されない（TL）。
- **見つかった不具合と修正。** 条件が表示の更新レートを報告値のまま比べていたため、数フレームごとにエポックが切り替わった。数えたフレームは5,421回の更新のうち975、フレーム時間は一つも帰属しなかった。整数のHzにして直した（DESIGN 21.18）。修正後の実機の記録は、エポック1つ、切替の取りこぼし0、24,939フレームを数え、内訳も合った（25,051 ＝ 開始前110 ＋ 境界2 ＋ 24,939）。
- **時間の出所。** `FrameTimingManager` は、Questでは**Mainの時間だけ**を返し、RenderスレッドとGPUの時間は返さなかった（24,939フレームのうち0）。XRのGPU時間は、ほぼ全フレームで返った（PCのLinkでは返らない）。遅れは4〜5フレームで、上限8を超えたものは無かった。
- **環境の値。** グラフィックスAPI `Vulkan 1.1.0 [512.837.9 (0x80345009)]`、GPUドライバは未取得（Windowsでだけ読む）、XRランタイム `Oculus` `207.298.0`、XR機器は未取得。
- **サービス自身の更新の時間。** Developmentのビルドで平均約41 µs。Releaseの値ではない。
- **確かめていないこと。** QuestのRelease、Questからの実送信、全シナリオ入りのパッケージ。
- **実機での導入。** 181 MBのAPKの導入が8回中4回失敗した（停止、またはヘッドセットがoffline）。失敗はどれもUnityのビルドが終わってから数分以内で、ケーブルの抜き差しの後は通った。原因は確かめていない。

同じ確認の中で、Fragmentのグループ回収がQuestで追いつかない問題が見つかった。これは統計とは別の変更として、DESIGN 7.10（D-232、D-233）に記録した。
